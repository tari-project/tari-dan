## What is Tari Ootle?

Tari Ootle is a **layer-2 execution layer**. It runs WebAssembly smart contracts — called
**templates** — over a sharded, account-and-object state model, and it anchors its security and
its supply of the native token to the Minotari base layer.

If you are coming from other ecosystems, the closest mental model is "a smart-contract chain
that does not produce its own consensus-independent security; it borrows a base layer for identity
and for the final say on value." Ootle is **not** a rollup: it does not post state roots to the
base layer, and the base layer does not re-execute or verify Ootle transactions. Ootle runs its
own Byzantine-fault-tolerant consensus among its own validator set.

Two layers, then, but not two copies of the same thing:

| Layer | Records | Model | Consensus |
|---|---|---|---|
| **Minotari** (base layer) | Assets — which coins exist and move | UTXO | Proof of work |
| **Ootle** (this layer) | State — what a program's data is right now | Objects and components | Chained BFT |

The base layer keeps a ledger of value. Ootle keeps a ledger of state: a key-value map from a
`SubstateId` to a versioned `Substate` (see
<a href={basePath("/concepts/state-and-execution/")}>State and Execution</a>). A transaction does
not move coins from column A to column B so much as it calls a component method and changes the
state of the objects it touches.

## The division of labour

The two layers are split deliberately, by trust surface.

**The base layer does the few hard things.** It is kept simple on purpose — a UTXO chain with a
weak script — so that there is little on the security anchor to attack. It provides:

- **Identity and registration.** Validator nodes register on the base layer, and that registration
  is what the Ootle epoch oracle reads to decide who is in a committee this epoch.
- **The minting source.** The only way to create the Ootle native token is to burn its base-layer
  counterpart. There is no reverse bridge (see
  <a href={basePath("/concepts/tokenomics/")}>Tokenomics</a>).
- **A liveness backstop.** A BFT chain can stall if more than a third of a committee misbehaves.
  The base layer's proof-of-work provides a reference point that keeps epochs advancing.

**Ootle does the programmable, high-throughput thing.** It owns execution, the sharded state, and
its own finality, and it isolates the complex, higher-risk logic — arbitrary contracts — away from
the anchor.

<Aside type="note">
The base-layer identifiers Ootle consumes — validator registrations, contract (template)
registrations — are read through an **epoch oracle**. In this repository you will see that
boundary as `crates/epoch_oracles/src/base_layer/oracle.rs`, which pulls the base-layer epoch
length and validator set. The base-layer chain itself lives in the upstream Minotari project.
</Aside>

Three things cross the seam, and it is worth naming what each one is *not*:

- **Membership** flows inward only. The base layer says who is registered; the oracle turns that into
  committee membership. Ootle never writes membership back.
- **Value** flows inward only. Burning a base-layer coin is the sole way to create L2 TARI. Nothing
  flows out.
- **State** does not cross at all. No state root, no proof, and no transaction is ever posted to the
  base layer for verification.

## The moving parts

Ootle is a network of cooperating node roles. Only one of them votes on state.

| Node | Role |
|---|---|
| **Validator node** | Runs the consensus protocol (HotStuff) and executes transactions within its shard group. This is the only role that produces finality. |
| **Indexer** | Tracks the chain, indexes transactions, substates, and events, and serves queries to clients. It does not vote. |
| **Wallet daemon** | Holds keys, builds and signs transactions, and talks to the indexer. It does not vote. |
| **Base-layer node** | The upstream Minotari node. Ootle nodes read registrations and epoch data from it. |

A deeper role-by-role breakdown, together with how nodes are grouped into shards, is in
<a href={basePath("/concepts/architecture/")}>Architecture</a>.

## Finality, briefly

Ootle reaches finality inside its own consensus, not on the base layer. A block becomes
irreversible when the validator committee's HotStuff chain grows far enough past it — under the
**three-chain rule**, a block is committed once a chain of three justified blocks is built on
top of it. Read the mechanism in detail in
<a href={basePath("/concepts/consensus/")}>Consensus</a>.

The base layer's role in finality is narrower: it decides *membership* (who is allowed to vote this
epoch) and it is the reference clock that epochs advance against. Safety of a state transition is a
statement about the Ootle committee; liveness borrows from the base layer.

## What "anchoring" does not mean

Because Ootle borrows identity and value from the base layer, it is easy to assume it also borrows
*verification*. It does not. Four negatives define the boundary:

| Ootle is not… | …which means |
|---|---|
| a rollup | No state root is posted to the base layer, so the base layer has no record of Ootle's state. |
| a validity proof | Ootle transactions are never re-executed on the base layer; there is no fraud proof or SNARK securing execution. |
| a sidechain needing base-layer finality | Ootle's finality comes from its own committee's three-chain rule, not from proof of work. |
| a settlement layer for the base coin | Value crosses inward only; the base layer keeps full control of its own supply. |

What Ootle *does* take from the base layer is narrower and more valuable than verification: a **single
canonical answer to "who is allowed to validate, right now"**, delivered on a clock both layers agree
on. That answer is what stops one committee from being swapped for another by an attacker, and it is
the only thing standing between a validator set and an identity free-for-all.

<Aside type="note">
The trade this buys: Ootle cannot be *silently* corrupted, because producing a conflicting final state
requires a quorum of a committee drawn from base-layer registrations. The price is that if a
committee loses more than a third of its members, Ootle stalls until the epoch boundary re-forms it —
a liveness cost, paid in time, not in safety. See
<a href={basePath("/concepts/consensus/")}>Consensus</a> for the arithmetic.
</Aside>

## The life of a transaction

The sections that follow each zoom into one stage. In order, a transaction:

1. **Is built and sealed.** A wallet daemon assembles instructions, attaches a separate stream of fee
   instructions, and signs. The signers' public keys become the transaction's *initial authorization
   scope* — the badges its access rules are checked against.
2. **Is submitted and gossiped.** The wallet hands it to an indexer, which checks its shape and
   propagates it over the `transactions` gossip topic to the committees holding its inputs.
3. **Is sequenced.** The relevant committee orders it into a block. If the inputs live in more than one
   shard group, the other groups first **pledge** not to touch them, so the parts commit together or
   not at all.
4. **Is executed.** The TVM runs the fee instructions first and checkpoints, then runs the main
   instructions. Metered work becomes the fee.
5. **Is committed.** Votes aggregate into a `ProposalCertificate`; the chain advances; the
   **three-chain rule** makes an earlier block irreversible.
6. **Is published.** The transaction's `SubstateDiff` writes new substate versions, and the receipt —
   including events — is served by indexers.

Each stage has a page: <a href={basePath("/concepts/consensus/")}>Consensus</a> for steps 3 and 5,
<a href={basePath("/concepts/state-and-execution/")}>State and Execution</a> for step 4 and 6, and
<a href={basePath("/guides/transaction-overview/")}>Transaction Overview</a> for how a client
performs steps 1 and 2.

## Where the value comes from

The native token on Ootle is **TARI** (a stealth resource). It enters the system through a one-way
path: burn the base-layer coin, claim a matching amount on Ootle. There is no peg-out — you cannot
burn TARI to recreate base-layer coins — so base-layer supply control stays entirely on the base
layer, and demand for TARI is anchored to the fee market. See
<a href={basePath("/concepts/tokenomics/")}>Tokenomics</a>.
